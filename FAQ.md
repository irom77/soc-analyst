# Case Analyzer FAQ

## Will the analyzer consider SOC analyst notes and comments, including a justification that something is not an issue?

Yes. The analyzer sends available SOC analyst notes and comments to the LLM as evidence:

- Top-level case `comments` are normalized into `case.comments`.
- The complete source export is retained in `case.source_data`, including parent notes, child-container notes, artifact notes, and comments.

The investigation prompt allows verdicts such as `False Positive` and `Benign`. A supported analyst explanation—such as activity being expected and associated with an approved change—can therefore influence the verdict.

An analyst's disposition is evidence, not an instruction that automatically overrides the telemetry. The LLM should evaluate whether the justification is supported, contradicted, or unverifiable using the rest of the exported case. A statement such as “not an issue” without supporting evidence may not be enough to produce a benign or false-positive verdict.

The current canonical schema does not distinguish analyst-authored notes from automation-generated notes or guarantee that the report explicitly says whether it accepted an analyst's justification. Source-specific authorship and note metadata remain available under `case.source_data` for the model to examine.

For the most useful result, include:

- who made the disposition;
- the reason for it;
- supporting evidence, such as an approved change or known administrative activity;
- the affected asset and relevant time range;
- evidence that would contradict the disposition, if known.

Always have an analyst verify the generated verdict before using it operationally.

## Why does the model name decide which provider is called?

Because the analyzer calls providers through the LiteLLM SDK, and LiteLLM reads
`CASE_ANALYZER_MODEL` as a **routing key** rather than as an opaque string forwarded to
`CASE_ANALYZER_BASE_URL`. That is what lets a provider with no OpenAI-compatible
endpoint be reached without a gateway:

    CASE_ANALYZER_MODEL=gemini/gemini-2.5-flash    # Google's native generateContent API

To keep that from changing the meaning of names already in use, the analyzer treats
only prefixes this project has verified as native — currently just `gemini/` — and
sends everything else down the OpenAI-compatible path to the configured endpoint:

| `CASE_ANALYZER_MODEL` | Route |
| --- | --- |
| `gemini-2.5-flash` | OpenAI-compatible, sent to `CASE_ANALYZER_BASE_URL` |
| `gemini-native` (a LiteLLM proxy alias) | OpenAI-compatible |
| `meta-llama/Llama-3` | OpenAI-compatible — a slash in an opaque model name is not a provider |
| `gemini/gemini-2.5-flash` | Google's native API; no base URL needed |
| `openai/<name>` | forces the compatible path |

The last row is the escape hatch for a collision. Some OpenAI-compatible gateways use
model IDs whose first segment happens to match a provider name — `anthropic/claude-3`,
for example. Such a name is sent to the configured endpoint unchanged, since
`anthropic/` is not on the verified list, but `openai/` is available if a future prefix
ever collides: LiteLLM strips only the leading segment, so `openai/gemini/x` reaches
the endpoint as `gemini/x`.

Existing configurations do not need to be edited. Defaulting to the OpenAI-compatible
route is deliberate — only a prefix that has been verified against a real provider run
should divert traffic away from the endpoint you configured.

## Does the CLI make two LLM calls like the Case Analysis Worker?

No. The standalone `case-analyzer` CLI makes one LLM call to generate the structured investigation report. Input normalization and loading an optional `--knowledge` JSON file happen locally and do not call the LLM.

The repository's Case Analysis Worker normally makes two LLM calls:

1. Generate search keywords from the serialized case.
2. Generate the investigation report from the case and knowledge records retrieved with those keywords.

The standalone CLI does not generate knowledge-search keywords or search the repository's Knowledge database because it is independent of Django and the repository database. To provide equivalent supporting context, export the relevant knowledge records as a JSON array and pass the file with `--knowledge`.

If the worker's keyword-generation call fails, it derives fallback keywords locally and continues to the report call. In that fallback path, only the report is successfully generated by the LLM.

## Is Case Analyzer just searching the case for suspicious keywords?

No. Case Analyzer is not a keyword-matching or keyword-scoring engine. It sends the normalized case—including alerts, artifacts, telemetry, notes, comments, and optional knowledge—to the LLM and asks it to produce a structured investigation report. The model should evaluate how the evidence relates, what conclusions it supports, which alternative explanations remain, and what information is missing.

Words such as “malware,” “critical,” or “attack” do not automatically produce a `True Positive` verdict. Likewise, a note saying “not an issue” or “known safe” does not automatically produce a `Benign` or `False Positive` verdict. These statements are contextual evidence that should be corroborated against technical facts such as process activity, network traffic, identities, assets, timestamps, artifacts, and enrichment results.

This is different from the Case Analysis Worker's first LLM call, which generates keywords solely to retrieve potentially relevant records from the Knowledge database. Those search keywords do not directly decide the verdict. The standalone CLI does not perform that knowledge-search call at all.

LLM reasoning is not completely immune to wording. Strong language, repetition, unsupported conclusions, or instruction-like text embedded in exported notes can influence a model. The defensible description is therefore **evidence-oriented semantic analysis rather than deterministic keyword matching**, not a guarantee that wording can never affect the result. An analyst should verify that the report's conclusions are supported by the underlying evidence.

Instruction-like text is not a theoretical risk. A recorded benchmark run on 2026-08-18 showed the configured model following directives embedded in case notes — returning a demanded verdict and reproducing attacker-supplied content — in every sample of two synthetic prompt-injection cases, while resisting alarming or reassuring *descriptions* throughout. In response, the system prompts now declare all case content untrusted data whose embedded directives must be reported rather than followed, and the request payload is sent between explicit untrusted-data markers. With both measures the same benchmark passes in full, on that model and those cases. The mitigations raise the bar; they do not make injection impossible, and `case-analyzer-evals` exists to re-measure whenever the prompt or model changes. See [`evals/baseline-2026-08-18.md`](evals/baseline-2026-08-18.md) for the recorded before-and-after results.

The [evidence-oriented reasoning examples](examples/reasoning/README.md) demonstrate this distinction with alarming-but-benign, reassuring-but-malicious, and alarming-but-incomplete cases, including results from a recorded live run.
